# Jarvis Orchestrator v1 — Design Specification

**Date:** 2026-08-19
**Status:** Founder-approved design
**Target branch:** `agent/agent-contract-v1`

## 1. Purpose

Jarvis Orchestrator v1 replaces the current fixed discovery chain with the smallest useful dynamic orchestration layer. The system accepts a Founder goal, produces a structured execution plan, routes work to registered specialists by capability, tracks dependencies and task state, enforces approval policy, and fails closed on invalid plans, missing routes, or execution errors.

This iteration does not attempt full autonomy. The goal is a deterministic execution core around an LLM-assisted Planner.

## 2. Locked Architectural Approach

Jarvis uses a hybrid model:

- The Planner may use the local LLM to propose structured tasks, required capabilities, dependencies, priorities, operations, and suggested risk.
- Deterministic core services validate the plan and decide what may execute.
- The Router may select only enabled agents that exist in the Agent Registry and satisfy capability and risk constraints.
- Approval policy may increase risk but may never be weakened by the Planner or an agent.
- Task Manager is the source of truth for task state and plan completion.
- Execution remains synchronous in v1, but task/dependency models are parallel-ready.

Core flow:

```text
Founder Goal
    ↓
Jarvis Orchestrator
    ↓
Planner
    ↓
ExecutionPlan
    ↓
Plan Validation
    ↓
Task Manager
    ↓
READY task
    ↓
Approval Service (pre-execution policy gate)
    ↓
Router ← Agent Registry
    ↓
Selected Agent
    ↓
MessageBus
    ↓
Agent Result
    ↓
Task Manager
    ↓
Approval Service (post-result gate when required)
    ↓
continue / WAITING_APPROVAL / FAILED / COMPLETED
```

## 3. Package Boundaries

Existing generic infrastructure remains under `core/`:

```text
core/
├─ contracts.py
├─ message_bus.py
└─ ollama_client.py
```

Jarvis-specific orchestration is introduced under:

```text
jarvis/
├─ __init__.py
├─ models.py
├─ registry.py
├─ router.py
├─ planner.py
├─ task_manager.py
├─ approvals.py
└─ orchestrator.py
```

Current agents remain under `agents/` and continue to inherit `BaseAgent`.

The existing `core/workflow.py` remains temporarily as a working legacy/reference path during migration. It is removed only after the new orchestrator path is proven and `main.py` is switched safely.

## 4. Domain Models

### 4.1 JarvisTask

`JarvisTask` represents work over time. `AgentMessage` represents communication. They are intentionally separate.

Required fields:

```text
id
plan_key
goal_id
parent_id
title
objective
operation
required_capabilities
dependencies
assigned_agent
status
priority
risk_level
requires_approval
input_data
result
error
created_at
started_at
completed_at
```

`id` is an internal UUID generated by Jarvis. `plan_key` is a unique human/Planner-readable key within one plan, such as `market_research`. Planner dependency references use `plan_key`; the plan parser validates them and converts them to internal task IDs before execution.

`operation` is an optional normalized operation name used by approval policy, for example `publish`, `credentials`, or `locked_core_change`. Ordinary analysis tasks may use `operation = null`.

`TaskStatus` in `core/contracts.py` is extended with `READY` and `BLOCKED` so Jarvis does not create a second competing task-status enum.

### 4.2 ExecutionPlan

Required fields:

```text
goal_id
goal
summary
tasks[]
requires_founder_approval
```

`goal_id` is generated by Jarvis. Individual agents cannot mutate the plan or mark the plan complete.

### 4.3 AgentRegistration

Required fields:

```text
name
agent_class
capabilities
allowed_risk_levels
enabled
metadata
```

Agent registrations are explicit in v1. No automatic Python module scanning is introduced.

### 4.4 OrchestratorState

Allowed v1 states:

```text
IDLE
PLANNING
EXECUTING
WAITING_APPROVAL
FAILED
COMPLETED
```

## 5. Planner

The Planner is advisory, not authoritative.

It receives a Founder goal and returns structured JSON that is converted into an `ExecutionPlan`.

Example Planner output:

```json
{
  "summary": "Research current Roblox opportunities",
  "tasks": [
    {
      "key": "market_research",
      "title": "Market research",
      "objective": "Identify promising Roblox opportunities",
      "operation": null,
      "required_capabilities": ["market_research"],
      "dependencies": [],
      "priority": "normal",
      "risk_level": "low",
      "requires_approval": false
    }
  ]
}
```

The parser/validator rejects:

- malformed JSON;
- missing required task fields;
- empty task lists where work is required;
- duplicate task keys;
- unknown capabilities;
- dependencies referencing non-existent task keys;
- self-dependencies;
- circular dependencies;
- invalid priority or risk values;
- invalid approval flags.

There is no permissive “try anyway” fallback in Jarvis Core.

Capability validation uses the currently enabled Registry capability catalog. A plan requiring unavailable capability is invalid in v1 rather than being silently routed to a partial match.

## 6. Agent Registry

The Registry is the authoritative catalog of available specialists.

It supports:

- explicit registration;
- duplicate-name rejection;
- lookup by name;
- capability lookup;
- disabled-agent exclusion;
- risk-level filtering.

Example:

```text
researcher
capabilities:
- market_research
- competitor_analysis
- concept_analysis
allowed_risk_levels:
- LOW
- MEDIUM
```

The initial registry may include the current Producer, Researcher, and Game Director, but the new orchestrator must not depend on a fixed chain.

## 7. Router

The Router receives a `JarvisTask` and the Registry.

V1 routing rules:

1. Consider only enabled agents allowed to handle the task's effective risk level.
2. Keep only agents whose capability set contains every capability required by the task.
3. Prefer an exact capability-set match.
4. Otherwise prefer the smallest capability superset.
5. Break any remaining tie deterministically by registration name.
6. If no agent satisfies the task, return structured `NO_ROUTE`.

V1 does not split one task among several partial matches. Team decomposition belongs to a later iteration.

The Planner may request capabilities. It may not choose a Python class or bypass the Registry.

## 8. Task Manager

Task Manager is the only source of truth for work status.

Responsibilities:

- store tasks for the active plan;
- determine which tasks are `READY`;
- prevent tasks from running before dependencies complete;
- transition tasks through runtime states;
- record assigned agent, result, timestamps, and errors;
- unlock dependents when prerequisites complete;
- mark dependent work `BLOCKED` when a prerequisite fails or is rejected;
- determine whether the plan is complete.

An agent may report only the result of its assigned task. It cannot mark the complete plan as finished.

V1 execution is synchronous, but dependencies are modeled explicitly so independent tasks can later be scheduled in parallel without redesigning the task contract.

## 9. Approval Service

Approval uses three values:

```text
Suggested Risk
Policy Minimum Risk
Effective Risk = max(Suggested Risk, Policy Minimum Risk)
```

Planner or agent output may never lower a policy minimum.

V1 policy minimums:

```text
publish                 HIGH
delete_important_data   HIGH
credentials             CRITICAL
security_policy_change  CRITICAL
locked_core_change      CRITICAL
paid_action             CRITICAL
```

Base behavior:

```text
LOW      → continue automatically
MEDIUM   → continue and append an in-memory audit record
HIGH     → WAITING_APPROVAL
CRITICAL → WAITING_APPROVAL + explicit Founder confirmation
```

### 9.1 Pre-execution gate

If a task's normalized `operation` has a HIGH or CRITICAL policy minimum, approval is required before the agent is allowed to execute that side effect.

### 9.2 Post-result gate

If `requires_approval=True`, the agent may produce its result, but the task does not unlock dependents until Founder approval. This supports recommendation/decision checkpoints such as Game Director concept approval.

### 9.3 Founder decisions

V1 supports structured decisions:

```text
APPROVE → release the pending gate and continue execution
REJECT  → mark the gated task REJECTED and block dependents
CHANGE  → stop at WAITING_APPROVAL and return the requested-change context to the caller; automatic replanning is deferred
```

CRITICAL approval requires an explicit confirmation flag in addition to `APPROVE`.

The Approval Service stores pending approval context and in-memory audit records. Persistent audit storage is deferred to SQLite work.

## 10. Orchestrator

`JarvisOrchestrator` is deterministic coordination code, not an LLM agent.

It may:

- accept a Founder goal;
- request a plan;
- validate the plan;
- load tasks into Task Manager;
- obtain the next READY task;
- calculate effective risk before execution;
- stop for pre-execution approval when required;
- request routing;
- deliver work through MessageBus;
- collect the resulting `AgentMessage`;
- update Task Manager;
- stop for post-result approval when required;
- apply Founder decisions;
- continue after an approved gate;
- stop on failure or rejection;
- continue until the plan completes.

It may not:

- invent permissions;
- execute unregistered agents;
- bypass approval policy;
- ignore dependencies;
- continue dependent work after prerequisite failure or rejection;
- modify LOCKED CORE on its own authority.

## 11. Error Handling

Core failures are structured and fail closed.

Examples:

```text
invalid plan       → PLAN_INVALID
no valid route     → NO_ROUTE
agent failure      → task FAILED
failed dependency  → dependent task BLOCKED
rejected approval  → task REJECTED + dependents BLOCKED
approval required  → orchestrator WAITING_APPROVAL
unrecoverable core → orchestrator FAILED
```

V1 does not automatically retry, reassign, spawn a debugger team, or replan after failure. It returns structured failure/change context to Jarvis/Founder. Those behaviors are later iterations.

## 12. Migration Strategy

Migration is deliberately reversible.

1. Build and test the new `jarvis/` subsystem while current `core/workflow.py` remains intact.
2. Preserve all existing Agent Contract v1 tests.
3. Add Orchestrator v1 tests.
4. Prove the new path end-to-end with mocked LLM output.
5. Switch `main.py` from `run_discovery_workflow()` to `JarvisOrchestrator` only after the new path is green.
6. Keep legacy workflow cleanup as a separate later change.

## 13. Testing Strategy

Use Python standard-library `unittest` and TDD.

Required coverage:

### Registry
- register agent;
- reject duplicate registration;
- exclude disabled agent;
- capability lookup.

### Router
- exact/full capability match;
- deterministic tie-breaking;
- missing capability returns `NO_ROUTE`;
- risk permission enforced.

### Planner
- valid JSON creates `ExecutionPlan`;
- malformed JSON fails safely;
- duplicate key rejected;
- invalid dependency rejected;
- dependency cycle rejected;
- unknown capability rejected.

### Task Manager
- READY task detection;
- dependency blocking;
- completion unlocks dependents;
- failure blocks dependents;
- rejection blocks dependents;
- plan completion is computed correctly.

### Approval Service
- LOW continues;
- MEDIUM continues and audits;
- HIGH waits;
- CRITICAL waits for explicit Founder confirmation;
- policy may raise risk;
- Planner cannot lower policy minimum;
- protected operation is gated before execution;
- post-result approval blocks dependents;
- APPROVE releases the gate;
- REJECT blocks dependent work.

### Orchestrator
- executes multiple sequential tasks;
- routes by capability rather than fixed agent names;
- stops on task failure;
- stops on pre-execution approval;
- stops on post-result approval;
- resumes after APPROVE;
- handles REJECT deterministically;
- returns CHANGE context without autonomous replanning;
- completes a valid plan;
- never runs disabled or unauthorized agents.

The existing 29 Agent Contract tests must continue to pass. The target total is approximately 55–65 tests, but correctness, not a fixed count, is the acceptance criterion.

## 14. Explicit Non-Goals for v1

Orchestrator v1 does not:

- create new agent classes automatically;
- allow autonomous code-writing agents;
- execute tasks in parallel;
- persist state to SQLite;
- push Git changes automatically;
- publish Roblox games automatically;
- implement the Game Factory;
- implement asset pipelines;
- implement LiveOps;
- combine multiple partial agents into one task team;
- automatically replan after CHANGE or failure.

These are intentionally deferred until the orchestration foundation is proven.

## 15. Definition of Done

Orchestrator v1 is complete when all of the following are demonstrated by automated tests and an end-to-end local run:

- Planner creates a structured validated plan.
- Task dependencies are enforced.
- Registry stores capability metadata.
- Router selects an enabled permitted agent by capability.
- Unknown/unavailable capability fails closed.
- Disabled agents are never selected.
- Risk permissions are enforced.
- Protected HIGH/CRITICAL operations cannot execute before approval.
- Failed or rejected tasks block dependent work.
- Post-result approval checkpoints prevent dependents from starting early.
- HIGH operations stop for Founder Approval.
- CRITICAL operations require explicit Founder confirmation.
- LOW tasks continue without manual intervention.
- APPROVE resumes the pending plan.
- The plan becomes `COMPLETED` only when all required tasks complete.
- The active workflow no longer requires hard-coded Producer → Researcher → Game Director handoffs.
- All pre-existing Agent Contract v1 tests remain green.

## 16. Next Layer After v1

After Orchestrator v1 is stable, the intended bootstrap sequence is:

```text
Developer Agent
Tester Agent
Reviewer Agent
    ↓
Git Worker
    ↓
Agent Factory
    ↓
Dynamic specialist expansion
    ↓
Roblox Master Template / Game Factory
```

This design keeps the orchestration core small enough to test rigorously while establishing the boundaries required for the larger Kreovanta Game Studio architecture.
